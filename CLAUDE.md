## Продукт

Статический генератор подписных `.ics`-фидов со сроками налоговой отчётности РК. Человек один раз подписывается на URL, соответствующий его режиму, и получает окна подачи и дедлайны с напоминаниями.

Без БД, без внешних API, без вычислений на запрос — раздача статики за CDN. Перегенерация инициируется человеком при изменении правил или добавлении календаря на новый год, несколько раз в год.

## Инварианты

Нарушение любого — критический дефект, на каждый нужен тест. Детали в `SPEC.md` §3.

**I1. `UID` детерминирован и вечен.** `{rule-id}-{period-key}@nalog-cal.kz`, например `fno-910-00-2026H1@nalog-cal.kz`. Никаких случайных значений, хешей от изменяемого содержимого, зависимости от времени генерации. При смене `UID` клиент удаляет событие и создаёт заново — пользователь теряет заметки и напоминания. **Один раз изменённый `UID` невозможно откатить у тех, кто уже подписан.**

**I2. Вывод побайтово стабилен.** Два прогона на неизменных входных данных дают идентичные файлы, иначе не работают `ETag` и `304`. Следствия: `DTSTAMP` берётся из поля `updated` правила, а не из системного времени; сортировка событий по `DTSTART`, затем по `UID`; никаких map-итераций без явной сортировки ключей.

**I3. Все даты — `VALUE=DATE`, не `DATE-TIME`.** Часовые пояса не используются, `VTIMEZONE` в выводе отсутствует. **`DTEND` не включается в интервал**: событие, заканчивающееся 17 августа, имеет `DTEND:20260818`. Самая частая ошибка в реализациях iCalendar и первый кандидат в тесты.

**I4. Событие не удаляется.** Отменённое обязательство получает `STATUS:CANCELLED` и остаётся в фиде. Удалённое событие исчезает молча, и пользователь не узнаёт, что обязательство снято.

**I5. `SEQUENCE` растёт только при содержательном изменении** — `DTSTART`, `DTEND`, `SUMMARY`, `STATUS`. Правки формулировок в описании и рефакторинг правил его не трогают.

**I6. Отсутствие данных — ошибка, а не пустой результат.** Нет производственного календаря на часть запрошенного диапазона → ненулевой код выхода и внятное сообщение. Недостающий год никогда не достраивается предположениями.

## Правила предметной области

- **Правило переходит в `data/rules` только с проставленной галочкой «Проверено» и заполненными `source` / `source_url`.** Правило без них не проходит валидацию.
- **`source_url` — исключительно adilet.zan.kz или kgd.gov.kz.** Вторичные публикации (mybuh.kz, pro1c.kz, uchet.kz) годятся, чтобы найти, какую статью читать, но в `source_url` не попадают.
- **Любая неоднозначность разрешается отказом сгенерировать событие, а не догадкой.** Пропущенный срок стоит пользователю денег: Налоговый кодекс в редакции 2026 года не предусматривает продления сроков сдачи.
- **Сдача и уплата — разные события с разными датами.** Разрыв в 10 дней реален (15 и 25 число). Каждое правило типа «сдача» требует явной проверки: есть ли парное правило «уплата» и на какую дату.
- **Пороговые события вне продукта.** Достижение порога НДС, утрата права на спецрежим, «проверьте свой оборот» — не попадают в фид. Сервис отвечает за даты, налогоплательщик — за факты о себе. Проверка при добавлении правила: это дата из кодекса — да; это зависит от того, что человек о себе знает — нет.
- **Имена файлов фидов не меняются.** `docs/samozanyaty.ics`, `docs/ip-uproshchenka.ics` и остальные — публичные URL, на которые уже подписаны люди.
- **Разрешение «оси → набор правил» происходит при каждой генерации, а не при подписке.** Конфиг подписки хранит позицию по осям; замороженный при подписке список правил означал бы, что человек никогда не узнает о новом обязательстве.
- Цифры в таблицах `EVENTS.md` и `TAXONOMY.md` §4 — **гипотезы**, включая номера ФНО: под кодексом 2026 года нумерация могла измениться.

## Архитектура

Каталоги созданы, содержимого почти нет (`SPEC.md` §2):

```
cmd/gen/main.go       заглушка, выходит с кодом 1
internal/rules/       загрузка и валидация правил
internal/workdays/    производственный календарь, next_working_day
internal/expand/      правило + диапазон → конкретные вхождения
internal/ics/         рендер VCALENDAR
data/rules/*.yaml     правила — пусто
data/workdays/*.yaml  производственный календарь по годам — пусто
docs/                 выход, публикуется через GitHub Pages из ветки master
testdata/golden/
```

Поток: `data/rules + data/workdays → загрузка → валидация → раскрытие → рендер → docs/*.ics`.

Единственный содержательно сложный алгоритм — `next_working_day`: сдвигать дату на день вперёд, пока она суббота, воскресенье, праздник или перенесённый выходной. Производственный календарь вносится вручную из ежегодного постановления Правительства, около пятнадцати записей на год.

## Команды

```bash
go build ./... && go vet ./...

# gen пока заглушка — этот вызов заработает по итогам Этапа 1
go run ./cmd/gen --rules data/rules --workdays data/workdays \
                 --out docs --from 2026-01-01 --to 2027-12-31

go test ./...
go test ./internal/workdays -run TestNextWorkingDay   # один тест

curl -I https://tzheldibayev.github.io/kuntizbe/test.ics   # Content-Type, ETag
```

Флаг обновления golden-файлов (`-update` или аналог) — соглашение, которое предстоит реализовать вместе с самими тестами.

`.gitattributes` содержит `*.ics -text`: git не должен нормализовать `CRLF` в фидах, иначе побайтовая стабильность (I2) недостижима. При добавлении новых типов выходных файлов проверять это же.

## Стек

Go. Зависимости минимальны: YAML-парсер и `github.com/arran4/golang-ical` для рендера. Библиотека берёт на себя сворачивание строк на 75 октетах, `CRLF` и экранирование текстовых значений — при ручной реализации это три отдельных источника трудноуловимых дефектов. Golden-тесты страхуют от изменения поведения библиотеки при обновлении версии.

## Тесты

Golden-файлы на каждый фид для фиксированного диапазона; детерминизм (два прогона — одинаковые байты); стабильность `UID` при правке `note` или `title`; табличные тесты переноса по всем праздникам и переносам каждого года в `data/workdays`; границы DATE-событий; валидация (правило без `source_url` отвергается, ссылка на несуществующий режим отвергается, диапазон вне покрытия календаря — ошибка).

Готовые кейсы переноса 2026 лежат в `EVENTS.md`: 15 фев → 16 фев (выходной), 25 мар → 26 мар (Наурыз), 15 авг → 17 авг (выходной), 15 ноя → 16 ноя (выходной). Праздничный случай обязателен — он ловит ошибку, которую проверка «не суббота и не воскресенье» пропускает.

Перед публикацией каждый фид проходит валидатор iCalendar и подписывается в macOS Calendar и Google Calendar.

## Зафиксированные решения

Не пересматриваются без новых данных (`PLAN.md`).

| Решение | Следствие |
|---|---|
| Правила, а не таблица дат | нет БД для фактов, есть YAML в git |
| Уплата — отдельное событие от сдачи | ~вдвое больше событий |
| Пороговые события вне продукта | сервис отвечает за даты, не за факты о пользователе |
| Все события — `VALUE=DATE` | часовых поясов нет, `VTIMEZONE` не генерируется |
| Токенизированные URL с первого внешнего показа | иначе подписчики неисчислимы навсегда |
| `DESCRIPTION` — только норма, ссылка, пояснение | коммерция живёт на странице подписки |
| Имя проекта — `kuntizbe` | не привязано к вертикали |

До гейта Этапа 4 общий код не выносится. Достаточно не хардкодить: `Source` как интерфейс, вертикали как реализации, домен и название в конфиге.
