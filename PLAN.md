## Зафиксированные решения

Приняты и не пересматриваются без новых данных.

| Решение | Следствие |
|---|---|
| Подписной `.ics`-фид, а не CalDAV | статика за CDN, подписка в одно нажатие — разбор ниже |
| Правила, а не таблица дат | нет БД для фактов, есть YAML в git |
| Уплата — отдельное событие от сдачи | ~вдвое больше событий, разрыв 10 дней реален |
| Пороговые события вне продукта | сервис отвечает за даты, не за факты о пользователе |
| Все события — `VALUE=DATE` | часовые поясов нет, `VTIMEZONE` не генерируется |
| Токенизированные URL с первого внешнего показа | иначе подписчики неисчислимы навсегда |
| `DESCRIPTION` — только норма, ссылка, пояснение | коммерция живёт на странице подписки |
| Имя проекта — `kuntizbe` | не привязано к вертикали |

### Почему подписка, а не CalDAV

Выбор долго существовал по умолчанию и не был записан. Записан 2026-08-11.

**Google Calendar не подключается к чужому CalDAV-серверу.** Он отдаёт свои календари по CalDAV, но добавить внешнюю CalDAV-учётку в веб-интерфейсе нельзя. Переход на CalDAV вычеркнул бы всех гугловых пользователей. `.ics`-фид едят все: Apple, Google, Outlook, Thunderbird, Яндекс.

**Порог подписки.** `webcal://` — одно нажатие. CalDAV — «Настройки → Учётные записи → Другое → Учётная запись CalDAV → адрес, логин, пароль». Для бесплатного сервиса, который пробуют между делом, это разница между «подписался» и «закрыл».

**Сервер против статики.** Архитектура из `SPEC.md` §2 — генератор пишет файлы, отдаёт CDN, ничего не крутится. CalDAV требует живого сервера с аутентификацией, хранилищем и коллекцией на каждого пользователя. Плюс аккаунты — а `TAXONOMY.md` специально проводит границу «сервис отвечает за даты, не за факты о пользователе».

**Цена аварии.** Упавший CDN — фид не обновился. Упавший CalDAV — у людей календарь отвалился с ошибкой авторизации.

**Против чего это решение слабо.** CalDAV решает обе проблемы, найденные на Этапе 0: коллекция пишется, значит будильники и заметки пользователя живут; синхронизация идёт минутами, а не неделей. Если окажется, что уведомления до подписчика не доходят вообще, CalDAV — первый запасной вариант, но ценой потери гугловой аудитории и появления сервера с аккаунтами.

**Третий путь, дешевле обоих.** Если ценность в напоминании, календарь может быть неподходящим каналом доставки. Почта или телеграм-бот отправляют уведомление сами, не спрашивая разрешения у клиента, и не требуют ни сервера с аккаунтами, ни настроек у пользователя. Календарь тогда остаётся тем, чем он хорош — показывает даты на месте, — а стучит отдельный канал. Рассматривать, если проверка дефолтного алерта Apple даст отрицательный результат.

## Этап 0 — Измерение и скелет

**Объём: один вечер, ~2 часа. Кода почти нет.**

Цель — узнать единственное, чего нет ни в одном RFC: через сколько клиенты реально забирают обновление.

1. `mkdir kuntizbe && cd kuntizbe && go mod init github.com/<user>/kuntizbe`
2. Каркас пакетов из SPEC, пустые файлы
3. Руками написать `docs/test.ics`: одно выдуманное событие, обязательно `X-WR-CALNAME`
4. Включить GitHub Pages: ветка `master`, папка `/docs`
5. `curl -I` — убедиться в `content-type: text/calendar`
6. Подписаться с iPhone **и** из Google Calendar
7. Поменять дату в файле, запушить, засечь время до появления у каждого
8. Отдельно: поменять `UID`, посмотреть, что произойдёт

**Гейт закрыт 2026-08-11 с поправкой.** Результаты — в `MEASUREMENTS.md`.

Пункт 8 пройден лично. Пункт 7 закрыт иначе, чем задумывался: интервалы обновления не измерялись, потому что выяснилось, что измерять нечего. `REFRESH-INTERVAL` игнорируют оба клиента — Apple ставит неделю независимо от содержимого фида, Google настройки не даёт. Задержка оказалась свойством клиента, на которое генератор не влияет, а не величиной, которую он задаёт.

Главная находка этапа не та, за которой шли: **оба клиента по умолчанию вырезают `VALARM`**. Напоминание не доходит ни до кого, кто не менял настройки. Это открытый вопрос к продукту, и он должен быть решён до Этапа 1 — см. `SPEC.md` §6 и `MEASUREMENTS.md` §5.

## Этап 1 — Первый настоящий фид

**Объём: 2–3 вечера.**

### 1.1 Верификация правил

Начать с блока **A** из `EVENTS.md` — СНР для самозанятых. Причина: это собственный статус, набор минимальный, и подписка на него будет реально использоваться.

Источник — только adilet.zan.kz. Заполнить `source` и `source_url`, проставить галочки.

**Если источники по режиму самозанятых окажутся противоречивы** — это само по себе результат за час. Переключиться на блок **B** (ИП на упрощённой декларации), он документирован лучше.

### 1.2 Производственный календарь 2026

`data/workdays/2026.yaml` — праздники и переносы из постановления Правительства. Около пятнадцати записей.

### 1.3 Перенос на рабочий день

`internal/workdays` + табличные тесты на четыре известных случая из `EVENTS.md`:

| Дата | Ожидаемый результат | Что проверяет |
|---|---|---|
| 15 февраля | 16 февраля | выходной |
| 25 марта | 26 марта | праздник (Наурыз) |
| 15 августа | 17 августа | выходной |
| 15 ноября | 16 ноября | выходной |

Праздничный случай обязателен: он ловит ошибку, которую проверка «не суббота и не воскресенье» пропускает.

### 1.4 Генератор

`rules → expand → ics → docs/`. Golden-тест на весь фид. Тест на детерминизм: два запуска, одинаковые байты.

**Гейт:** собственный фид лежит на Pages, ты на него подписан, даты в нём верны и проверены по кодексу.

**Гейт закрыт 2026-08-11.** `docs/samozanyaty.ics` на Pages, автор подписан и лично сверил даты (в частности — двухдневный перенос октябрьского срока на 27 число из-за совпадения Дня Республики с воскресеньем). ## Этап 3 — Инфраструктура перед первым внешним человеком

**Ничего из этого не нужно, пока пользователь один. Всё из этого нужно до того, как ссылка уйдёт наружу.**

1. **Домен.** URL фида — вечное обязательство. Переезд после публикации теряет часть подписчиков молча.
2. **Cloudflare** вместо Pages: R2 или Workers для раздачи, KV для токенов. На Pages подписчиков сосчитать невозможно.
3. **Токены.** 16 случайных байт, base64url, версия схемы в пути: `/f/1/{token}.ics`. Хранят ссылку на конфиг, а не сам конфиг.
4. **Страница подписки.** Выбор режима человеческим языком, без номеров форм. Кнопка на `webcal://`, рядом ссылка для копирования.
5. **Страница управления** `/f/1/{token}/manage`: сменить режим, отписаться. Без пароля, токен сам себе доступ.
6. **Дисклеймер и политика.** Справочный характер, ссылка на первоисточник в каждом событии, что именно логируется.
7. **Учёт активности:** запись `(token, date)` раз в сутки. Метрика — токены с активностью за последние 60 дней.

**Гейт:** можешь назвать число активных подписок.
