# SPEC — Налоговый календарь РК

Генератор подписных `.ics`-фидов со сроками налоговой отчётности Республики Казахстан.

Человек подписывается один раз на URL, соответствующий его налоговому режиму, и получает в свой календарь окна подачи и дедлайны с напоминаниями. Дальше он о сервисе не вспоминает — и это правильное поведение продукта.

---

## 1. Принципы

Три правила, которым подчинено всё остальное.

**Корректность важнее функциональности.** Пропущенный срок стоит пользователю денег: Налоговый кодекс в редакции 2026 года не предусматривает продления сроков сдачи. Неверная дата в фиде — это не баг, это ущерб. Любая неоднозначность разрешается в сторону отказа сгенерировать событие, а не в сторону догадки.

**Каждая дата имеет первоисточник.** У каждого правила есть ссылка на норму и URL. Они попадают в `DESCRIPTION` события. Пользователь всегда может проверить.

**Даты вычисляются из правил, а не хранятся списком.** Срок сдачи — это норма кодекса («не позднее 15 числа второго месяца, следующего за отчётным периодом»), а не таблица. Правило кодируется один раз и раскрывается на любой диапазон лет.

---

## 2. Архитектура

Статический генератор. Один Go-бинарь, запускается вручную, пишет файлы в каталог.

```
data/rules/*.yaml          правила
data/workdays/YYYY.yaml    производственный календарь
        │
        ▼
   gen (Go)                загрузка → валидация → раскрытие → рендер
        │
        ▼
docs/*.ics                 готовые фиды → GitHub Pages / R2 / CDN
```

Без базы данных. Без внешних API. Без вычислений на запрос. Раздача — статика за CDN.

Перегенерация происходит при изменении правил или при добавлении календаря на новый год. Оба события случаются несколько раз в год и инициируются человеком.

### Структура проекта

```
cmd/gen/main.go
internal/rules/       загрузка и валидация правил
internal/workdays/    производственный календарь, перенос на рабочий день
internal/expand/      правило + диапазон → конкретные вхождения
internal/ics/         рендер VCALENDAR
data/rules/
data/workdays/
docs/                 выход, публикуется через Pages
testdata/golden/
```

### CLI

```
gen --rules data/rules \
    --workdays data/workdays \
    --out docs \
    --from 2026-01-01 \
    --to 2027-12-31
```

## 3. Инварианты

Нарушение любого из них — критический дефект. На каждый нужен тест.

### I1. UID детерминирован и вечен

```
UID:{rule-id}-{period-key}@nalog-cal.kz
UID:fno-910-00-2026H1@nalog-cal.kz
```

Собирается из идентификатора правила и ключа периода. Никаких случайных значений, никаких хешей от изменяемого содержимого, никакой зависимости от времени генерации.

При смене `UID` клиент удаляет событие и создаёт заново. Измерено на Этапе 0 (`MEASUREMENTS.md` §4): в Apple Calendar это проходит молча и чисто — дубля не остаётся, уведомления нет, потерять нечего, потому что подписной календарь read-only.

Инвариант тем не менее в силе. Проверен один клиент одной версии, на событии в будущем; непроверенными остались клиенты, не удаляющие исчезнувшее событие (там будет дубль), и смена `UID` рядом с датой, когда будильник уже отклонён. Стабильный `UID` не стоит ничего, а один раз изменённый невозможно откатить у тех, кто уже подписан. Дешёвая страховка от невозвратной ошибки.

### I2. Вывод побайтово стабилен

Два запуска генератора на неизменных входных данных дают идентичные файлы. Это обеспечивает работу `ETag` и ответов `304`, без которых раздача перестаёт быть бесплатной, а клиенты видят непрерывную ложную активность.

Следствия:
- `DTSTAMP` берётся из поля `updated` правила, а не из системного времени;
- порядок событий детерминирован — сортировка по `DTSTART`, затем по `UID`;
- никаких map-итераций без явной сортировки ключей.

### I3. Все даты — DATE, не DATE-TIME

Срок сдачи — это календарный день, а не момент времени.

```
DTSTART;VALUE=DATE:20260815
DTEND;VALUE=DATE:20260818
```

Часовые пояса не используются. `VTIMEZONE` в выводе отсутствует.

**`DTEND` для DATE-событий не включается в интервал.** Событие, заканчивающееся 17 августа, имеет `DTEND:20260818`. Это самая частая ошибка в реализациях iCalendar и первый кандидат в тесты.

### I4. Событие не удаляется

Отменённое или отменённой нормой обязательство получает `STATUS:CANCELLED` и остаётся в фиде. Удалённое событие исчезает из календаря молча, и пользователь не узнаёт, что обязательство снято.

### I5. SEQUENCE растёт только при содержательном изменении

Инкремент при изменении `DTSTART`, `DTEND`, `SUMMARY` или `STATUS`. Правки формулировок в описании и рефакторинг правил `SEQUENCE` не трогают.

### I6. Отсутствие данных — это ошибка, а не пустой результат

Если запрошен диапазон, для части которого нет производственного календаря, генератор завершается с ненулевым кодом и внятным сообщением. Он никогда не достраивает недостающий год предположениями.

## 4. Модель правила

```yaml
- id: fno-910-00
  title: "ФНО 910.00 — упрощённая декларация"
  regimes: [ip-uproshchenka, too-uproshchenka]
  period: half-year
  window_opens: null
  due:
    months_after_period_end: 2
    day: 15
  shift: next-working-day
  source: "НК РК, ст. 688 п. 1"
  source_url: "https://adilet.zan.kz/rus/docs/..."
  updated: 2026-01-15
  note: >
    Сдаётся дважды в год за полугодие. Отражает доход от деятельности
    и исчисление социальных платежей за самого ИП.
```

**`period`** — `month`, `quarter`, `half-year`, `year`.

**`window_opens`** — дата открытия окна подачи, если норма её устанавливает. Для ФНО 300.00 это 15 число месяца, следующего за кварталом: раньше подать нельзя. `null` означает, что окно не ограничено снизу.

**`shift`** — `next-working-day` или `none`. Правило переноса, когда расчётная дата выпадает на выходной или праздник.

**`source` и `source_url` обязательны.** Правило без них не проходит валидацию.

**`updated`** — дата последнего содержательного изменения правила. Источник для `DTSTAMP`.

### Ключи периодов

Строки, стабильные навсегда: `2026-01`, `2026Q1`, `2026H1`, `2026`.

## 5. Производственный календарь

```yaml
year: 2026
holidays:
  - date: 2026-01-01
    name: "Новый год"
  - date: 2026-03-21
    name: "Наурыз мейрамы"
transfers:
  - from: 2026-01-02
    to: 2026-01-10
    kind: rest        # выходной перенесён
```

Данные вносятся вручную из ежегодного постановления Правительства РК. Около пятнадцати записей на год.

### Перенос на рабочий день

Единственный содержательно сложный алгоритм проекта.

```
next_working_day(d):
    пока d — суббота, воскресенье, праздник или перенесённый выходной:
        d += 1 день
    вернуть d
```

Реальный пример: срок сдачи отчётности за 2 квартал 2026 года формально приходится на 15 августа, суббота, и переносится на понедельник 17 августа.

**Правовая основа переноса — НК РК, ст. 64 п. 2.** Не общая норма о выходных (Закон РК «О праздниках в Республике Казахстан», ст. 5), а прямая налоговая: «если последний день срока приходится на нерабочий день, то днем окончания установленного срока исполнения налогового обязательства считается ближайший следующий за таким днем рабочий день». Там же (п. 3) — налогоплательщик вправе исполнить обязательство досрочно, а по электронным каналам (кабинет налогоплательщика) — независимо от того, рабочий день или нет, до 24:00 последнего дня срока. Отсюда следствие для продукта: подать/уплатить в промежуточный нерабочий день (между расчётной датой и фактическим сроком) не запрещено и не является нарушением — фид показывает крайний срок, а не единственно возможный день.

Сюда идут табличные тесты, покрывающие все праздники и все переносы каждого загруженного года.

## 6. Форма события

**Есть `window_opens`** — событие охватывает окно подачи:

```
DTSTART;VALUE=DATE:20260715
DTEND;VALUE=DATE:20260818
SUMMARY:ФНО 300.00 — окно подачи за 2 квартал
```

**Нет `window_opens`** — однодневное событие на дату дедлайна:

```
DTSTART;VALUE=DATE:20260817
DTEND;VALUE=DATE:20260818
SUMMARY:ФНО 910.00 — срок сдачи за 1 полугодие
```

### Напоминания

Два `VALARM` на событие: за 7 дней и за 1 день.

```
BEGIN:VALARM
TRIGGER:-P7D
ACTION:DISPLAY
DESCRIPTION:Через неделю — ФНО 910.00 за 1 полугодие
END:VALARM
```

Напоминание и есть продукт. Дату человек способен найти сам; ценность в том, что она приходит к нему вовремя без усилий.

> **Измерено на Этапе 0 и не решено.** iOS вырезает `VALARM` при подписке (тумблер «Удалить напоминания» включён по умолчанию), Google Calendar уведомления подписного календаря тоже отключает. То есть напоминание **не доходит ни до кого**, кто не полез в настройки. Либо страница подписки явно этому учит, либо тезис выше требует переформулировки. Решить до начала кодирования правил — см. `MEASUREMENTS.md` §5.

### Описание

`DESCRIPTION` содержит норму, URL первоисточника и пояснение из `note`. Экранирование по RFC 5545: `\n` для переносов, экранируются `,` `;` `\`.

## 7. Фиды

Один файл на режим. Имя файла стабильно и никогда не меняется — это публичный URL, на который уже подписаны люди.

```
docs/samozanyaty.ics
docs/ip-uproshchenka.ics
docs/ip-uproshchenka-nds.ics
docs/ip-our.ics
docs/too-uproshchenka.ics
docs/too-our-nds.ics
```

Заголовок календаря:

```
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//nalog-cal.kz//tax-calendar//RU
CALSCALE:GREGORIAN
METHOD:PUBLISH
X-WR-CALNAME:Налоги — ИП на упрощёнке
X-WR-CALDESC:Сроки налоговой отчётности РК. Источник указан в каждом событии.
REFRESH-INTERVAL;VALUE=DURATION:P1D
X-PUBLISHED-TTL:P1D
```

`X-WR-CALNAME` обязателен: без него клиент подписывается на «Untitled Calendar». Проверено на Этапе 0 — доезжает и в Apple, и в Google.

`REFRESH-INTERVAL` и `X-PUBLISHED-TTL` **декоративны**: Apple их игнорирует и обновляет раз в неделю, Google интервал не настраивает вовсе. Оставлены, потому что часть клиентов их учитывает и вреда нет.

Практическое следствие — не техническое, а дисциплинарное: **исправление ошибочной даты доезжает до подписчика в худшем случае через неделю.** Правка правил должна выходить с запасом по времени; сценарий «выкатить фикс за день до срока» не работает в принципе.

### Раздача

```
Content-Type: text/calendar; charset=utf-8
ETag: <хеш содержимого>
Last-Modified: <дата последнего изменения правил>
```

Ответ `304` на условный запрос. Проверка перед публикацией:

```bash
curl -I https://<host>/ip-uproshchenka.ics
```

## 8. Тесты

**Golden-файлы.** Полный ожидаемый `.ics` на каждый фид для фиксированного диапазона дат. Любое изменение вывода становится видимым в diff.

**Детерминизм.** Два запуска подряд дают идентичные байты.

**Стабильность UID.** Изменение `note` или `title` правила не меняет ни одного `UID` в выводе.

**Перенос на рабочий день.** Табличные тесты по всем праздникам и переносам каждого года в `data/workdays`.

**Границы DATE-событий.** Однодневное событие имеет `DTEND` на следующий день. Событие-окно заканчивается днём после дедлайна.

**Валидация.** Правило без `source_url` отвергается. Правило со ссылкой на несуществующий режим отвергается. Диапазон вне покрытия производственного календаря завершается ошибкой.

**Внешняя проверка.** Каждый сгенерированный фид проходит валидатор iCalendar и подписывается в macOS Calendar и Google Calendar перед публикацией.

## 9. Публикация

Репозиторий публичный, GitHub Pages из ветки `master`, папка `/docs`.

На корневой странице `docs/index.html`:

- список фидов с кнопками подписки. Кнопка ведёт **только на `webcal://`**: измерено на Этапе 0, что по `https://` Google Calendar не подписывается вообще, а macOS делает разовый импорт без обновлений — в обоих случаях молча. Прямую ссылку оставить рядом для копирования, но не кнопкой;
- краткое описание каждого режима человеческим языком, без номеров форм — человек знает, что он «ИП на упрощёнке с сотрудником», а не что он «910.00 плюс 200.00»;
- дата последнего обновления правил;
- уведомление: сервис носит справочный характер, каждое событие содержит ссылку на первоисточник, ответственность за соблюдение сроков лежит на налогоплательщике.

## 10. Стек

Go. Зависимости минимальны: YAML-парсер и `github.com/arran4/golang-ical` для рендера. Библиотека берёт на себя сворачивание строк на 75 октетах, `CRLF` и экранирование текстовых значений — при ручной реализации это три отдельных источника трудноуловимых дефектов.

Golden-тесты страхуют от изменения поведения библиотеки при обновлении версии.
